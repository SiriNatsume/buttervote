# 提名内容同步修复

管理员“管理选项”原来只修改 `candidates`，提名页和“我的提名”读取的 `nominations` 因而保留旧内容。提交表单的成功卡片也保留了提交时的本地副本，不随服务端刷新更新。

迁移 `sync_candidate_nomination_content` 在候选内容更新的同一个事务中，同步同活动、同 `nomination_id` 的名称、简介、提名者显示名和图片元数据。不改变审核状态、提交人、原提交时间、拒绝理由、候选启停或继承关系。不创建候选项，不沿继承链修改源活动。内部触发函数位于私有 schema，撤销客户端直接执行权限。

提名页把当前用户的最新提名摘要传给成功卡片。卡片收到刷新数据后采用最新内容与状态；未提交的草稿和上传状态保持独立，刷新尚未到达时仍显示操作返回值。被拒绝的记录也参与展示更新，但仍不占用提名名额。管理员修改同时使提名页及个人提名入口失效。个人提名和成功卡片的图片 URL 带记录更新时间；同路径重传即使尺寸、文件大小不变也会更新版本，版本不变时继续复用图片缓存。

性能方面，不新增轮询。原有列表与个人记录读取改为并行，均使用既有过滤条件；个人摘要按当前用户和活动读取并完整分页，不读取他人的私有记录。客户端按 props 变化复用 ID 查找表，不在每次输入时重新构建。同步按提名主键更新至多一行，仅监听候选内容字段，普通投票和报票不经过该触发器。本地五次事务回滚样例中，同步触发器执行时间为 1.598 / 0.583 / 0.307 / 0.327 / 0.698 ms；这不是生产延迟承诺。

验证：

- 216 项回归全部通过，包含成功卡片四种状态、空内容/图片清除、同路径图片版本、操作结果回退及草稿保护；生产 OpenNext 构建及类型检查通过。
- `node --env-file=.local/supabase-app.env scripts/verify-nomination-sync.mjs` 验证四种审核状态的字段同步、提交元数据保留、空值、软删除状态、继承边界、无关联/跨活动关联、失败回滚和非管理员权限；测试仅允许本地 Supabase，并清理自建样本。
- 浏览器复现保存后原提名仍显示旧简介；修复后管理员实际保存名称、简介及显示名，已有提名与“我的提名”显示最新值。保留的成功卡片在后续正常刷新中更新为新名称和已拒绝状态，提名名额随之释放，未发现新增控制台错误。
- 本地数据库 advisors 没有关于新触发器的发现。新代码 lint 无新增诊断；“我的提名”列表已有的 `react-hooks/set-state-in-effect` 错误及管理员 actions 中两条未使用声明提示在基线提交同样存在，未通过禁用规则掩盖。

发布时先应用兼容旧应用的触发器迁移，再合并应用修复，由现有 Cloudflare 自动部署。历史记录修正独立于结构迁移，限定到用户提供的活动及已核实的记录，并在修正前保留旧值、核验当前候选内容，避免覆盖并发编辑。
