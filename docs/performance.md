# 访问性能优化（2026-10-18）

本轮覆盖全站加载、首页、活动组、独立活动、投票与结果，以及后台审核、投票记录、候选管理和成员统计。

## 实现

- 全站布局直接输出页面框架，导航和账号区分别通过 Suspense 加载；首页对阵图独立流式输出，并复用原有对阵图几何尺寸作为占位，减少内容移动。相关行为参见 [Next.js 15 数据获取与流式渲染](https://nextjs.org/docs/15/app/getting-started/fetching-data)。
- 使用 React 请求内缓存复用 Supabase 客户端、当前用户、当前资料和赛事图；公共导航与首页设置合并读取。每个新请求仍重新校验身份与设置。
- app session 的有效期、撤销状态和对应 profile 合并为一个关系查询；账号菜单通过至多一条拒绝提名记录判断通知。关系查询参见 [Supabase Joins and Nested tables](https://supabase.com/docs/guides/database/joins-and-nesting)。
- 赛事对阵图、独立与联合投票实时分数，以及普通用户和管理员结果页统一使用 `get_visible_contest_tallies` RPC。排名和同分排序复用原计票逻辑；进行中的结果只输出基础分，完整明细继续受结果可见性控制。实际管理员覆盖可以读取停用候选项的历史分数。
- 聚合 RPC、个人进度及导航的完整列表查询携带精确总数，使分页读取在末页结束；继续支持服务端返回行数小于请求页大小的情况。
- 活动组内容、关联页面、参与权限和对阵图并行加载；赛事图复用已经取得的候选项并并行读取参赛项，减少候选项谱系的重复请求。
- Noto Sans SC 使用可变字重，字体 CSS 从约 363 KiB 减至 91 KiB（未压缩文件）。活动封面及候选图片延迟加载并异步解码，首页主图使用高优先级。
- 回到顶部的滚动检查合并到每个动画帧，唱票页在隐藏标签页中暂停轮询。
- 后台审核每次读取 51 条以展示 50 条，使用 `(created_at, id)` 游标前后翻页，并单独统计完整待审总数。管理员投票记录按每页 50 条读取，只加载当前页提交人的资料，原始选票 payload 由数据库汇总处理。
- 候选管理通过受权限保护的 RPC 读取有历史票的候选项 ID；用户组列表通过 RPC 获取总人数和有效人数，覆盖永久、过期和撤销成员。
- 新增待审提名部分索引和投票记录复合索引。相关汇总函数保持 `SECURITY INVOKER`、固定 `search_path` 和实际管理员校验。

## 测量方法

同一台机器、Node.js 24、Next.js 15.5.18 生产构建、本地隔离 Supabase。为模拟应用到数据库的往返开销，对每个上游 fetch 加入固定 80 ms 延迟。逐页串行请求，每个场景预热一次、采样三次，以下为完整 HTML/RSC 响应耗时的中位数。数据库请求数从本地上游 fetch 记录统计。

这些数字用于比较本次代码变更；浏览器 LCP、INP、资源下载和 Cloudflare 部署位置需要在真实环境中另外测量。

## 第一阶段：9000 票赛事

三种投票方式各 3000 张票、9 名候选项，包含真爱票。比较相同规模与数值的临时赛事数据。

| 场景 | 优化前完整响应 | 优化后完整响应 | 上游请求数 |
| --- | ---: | ---: | ---: |
| 首页（配置赛事对阵图） | 2080 ms | 709 ms | 31 → 17 |
| 活动组（配置赛事对阵图） | 2270 ms | 702 ms | 33 → 18 |

优化后同规模的公共组内结果列表完整响应中位数为 489 ms。公共分组计票路径的上游记录已确认使用汇总 RPC。

## 第一阶段：已登录用户的常规页面

| 页面 | 优化前完整响应 | 优化后完整响应 | 上游请求数 |
| --- | ---: | ---: | ---: |
| 首页 | 811 ms | 568 ms | 22 → 13 |
| 活动组 | 460 ms | 287 ms | 14 → 11 |
| 活动组结果 | 540 ms | 381 ms | 12 → 9 |
| 联合投票 | 639 ms | 470 ms | 16 → 13 |
| 活动详情 | 630 ms | 561 ms | 15 → 12 |
| 冠军殿堂 | 541 ms | 185 ms | 7 → 5 |
| 登录页 | 453 ms | 192 ms | 7 → 4 |

共享布局解除阻塞后，常规页面开始返回响应的中位数由约 270–540 ms 降至约 8–14 ms。低数据量访客首页和活动详情的完整响应在本轮测量中基本持平；主要收益来自更早开始渲染、登录资料复用，以及大数据量计票路径。

## 第二阶段：非首页场景

以下比较以第一阶段代码为基线，继续使用每个上游请求增加 80 ms 的相同测量方法。测试数据包含 15000 张票（每个活动 3000 张）、1200 条临时提名和 1200 条成员记录。HTML/RSC 大小为解压后的响应正文，不等同于压缩后的网络传输量。

| 场景 | 完整响应中位数（前 → 后） | HTML/RSC 大小（前 → 后） | 上游请求数（前 → 后） |
| --- | ---: | ---: | ---: |
| 单活动结果（分组） | 953 → 420 ms | 65 KB → 65 KB | 13 → 11 |
| 独立活动结果 | 885 → 410 ms | 61 KB → 61 KB | 12 → 9 |
| 独立活动实时投票 | 694 → 514 ms | 46 KB → 46 KB | 14 → 11 |
| 管理员结果与投票记录 | 1276 → 420 ms | 3.67 MB → 141 KB | 17 → 14 |
| 后台候选管理 | 200 → 203 ms | 77 KB → 78 KB | 7 → 7 |
| 后台提名审核 | 594 → 423 ms | 9.55 MB → 1.03 MB | 9 → 10 |
| 用户组成员统计 | 381 → 204 ms | 156 KB → 156 KB | 9 → 6 |
| 管理员活动组结果 | 1404 → 515 ms | 68 KB → 68 KB | 22 → 11 |

审核页以额外一次总数查询换取有界的数据读取和渲染。本地队列合计 1215 条，已经完整遍历 25 页，验证无重复、无遗漏、倒序返回及失效游标回到首批的行为。翻页后批量选择会清空。

候选管理耗时基本持平；主要收益是将上限 1000 张完整选票替换为被引用候选项的 ID，并正确识别只出现在第 1000 张之后的历史票。管理员结果与投票记录已避免读取所有原始选票。

## 验证

- 138 项测试通过，包含三种投票方式、整数和小数权重、汇总与原算法的一致性、隐藏真爱票明细和缺失汇总的处理。
- 两阶段分别以 9000 和 15000 张本地测试票逐项核对汇总与原始计票；已发布、实时公开、隐藏、管理员覆盖和停用候选项场景的边界检查通过。项目原有结果可见性集成测试通过。
- app session 有效、过期、撤销、下一请求观察撤销，以及管理员进入管理页的检查通过；首页账号区与侧栏每次共享一次 session 查询。
- TypeScript 检查和生产构建通过；变更文件 lint 为 0 错误，保留既有原生图片警告。
- 浏览器核对首页、比赛详情浮层、活动组与结果列表，以及后台审核全选后翻页清空选择、投票记录翻页、成员统计、历史票提示和独立投票表单；相关页面无新增控制台错误。
- 本地临时赛事、测试票、提名、成员和会话在验证后清理，核对原始表行数；首页设置恢复。
- 最终数据库 Advisor 保留 27 条既有告警（RLS 初始化计划、重复许可策略和旧函数搜索路径），没有指向本次新增或替换对象的告警。新函数已核对为 invoker，分页查询命中新增索引。

当前线上普通脚本请求返回 HTTP 403，未将其耗时作为应用性能指标。发布后的真实用户表现仍待线上复测。

## 复测命令

在生产模式本地预览启动后运行：

```bash
node scripts/benchmark-pages.mjs --runs 5
node scripts/benchmark-pages.mjs --path / --path /login --path /groups/GROUP_ID --output .local/performance/pages.json
```

脚本默认仅访问本机，使用串行 GET 请求并输出开始返回与完整响应的中位数和 P95；可用 `--base` 指定明确的目标站点。已登录测量通过 `BUTTERVOTE_BENCHMARK_COOKIE` 环境变量传入当前测试会话，报告仅记录是否携带会话。

可重复验证 SQL、权限和分页：

```bash
node scripts/verify-performance.mjs
node scripts/verify-performance.mjs --pages
```

该脚本只读取 `.local/supabase-app.env` 并拒绝非回环 Supabase 地址，创建带随机 ID 的专属测试记录，在 `finally` 中校验归属、清理并核对原表行数。`--pages` 需要本地生产预览运行在 `http://127.0.0.1:3000`。执行前应已应用本次 SQL 迁移。

## 发布依赖

先应用 `supabase/migrations/20261018023743_page_performance_aggregates.sql`，再发布应用代码。该文件扩展汇总到独立活动、提供两个管理员汇总 RPC，并创建两个分页索引。

本地验证阶段在本机 PostgreSQL 事务中验证了迁移 SQL。2026-10-18 生产项目已应用 `page_performance_aggregates`；应按迁移名称核对远端历史，避免因本地与远端时间戳不同而重复执行。CLI 本地历史中已有两项早先迁移未登记，本次未批量应用或修复它们。后续应用发布通过 PR 审查、合并到 `main` 后由 Cloudflare 自动部署，具体流程见 [部署说明](./deployment.md)。

发布后检查首页、账号、投票、审核分页与结果可见性，再从实际使用网络测量完整响应与浏览器指标。
